# 実装計画

## 原則

publicリポジトリを前提に秘密・実データを残さず、変更操作は読み取りから段階的に分離します。各段階で対象Redmineのバージョン、独自改修、API、権限、カスタム項目を実機検証し、その結果が承認されるまで次段階を本番利用しません。APIキーの権限はツールでは制限できません。

## PR-1: 基盤・読み取り専用出力

- Python CLI、厳格なURL/TOML検証、環境変数または非表示入力によるキー取得
- GET限定クライアント、認証check、プロジェクト必須のexport
- 全ステータス、既定の子プロジェクト除外、任意トラッカー、固定ソート
- 防御的ページングと上限、選択項目だけのUTF-8 BOM付きCSVとUTF-8 JSON、実行単位の一意なrunディレクトリ公開
- HTTPをモックした異常系・機密非表示・出力テスト、Windows/CA/proxy/実機確認文書

受入条件は、全自動テスト通過、GET以外が存在しないこと、未完取得が出力されないこと、チェックリストの確認結果が「未実施」と明記されることです。

## PR-1.1: 実機確認結果と読み取り専用UX

- Windows 11での初回導入、PC再起動/新規PowerShell後の再開、実機照合runbook
- 固定GET endpointによるproject identifier/数値IDの安全なresolution
- APIの `created_on` / `updated_on` raw値を保持した、明示opt-inのJST表示列
- basic schemaを維持しながら標準追加項目、本文、custom field、個別issue情報を許可リストで段階導入する設計

許可するHTTP操作は `GET /users/current.json`、`GET /issues.json`、
`GET /projects/{id_or_identifier}.json` だけです。変更候補生成、変更系API、個別issue endpointは
追加せず、PR-2の計画も変更しません。

## PR-1.2: extended standard fields

- 既定のbasicを完全に維持し、明示 `--fields extended` だけで標準10項目を固定許可リスト出力
- 欠損/null/非null値をJSONと値なしmetadata集計で区別し、型・範囲・長さを安全に検証
- 既存JST opt-inとの直交した組合せ、固定CSV列、HTTPをモックした互換・異常系テスト
- QUICK2での返却shape、権限差、GUIとの業務的対応は未確認で、マージ後に承認済み少数件で確認

許可GET endpointと検索条件を増やさず、本文、custom field、個別issue情報、変更候補は対象外とする。

## PR-1.3: Windows・VPN環境での起動とプロキシ手順の整備

- Windows PowerShell 5.1の固定パラメータ起動補助。配置場所のvenv/configを使用
- 既定Inheritは従来のRequests選択を保持。明示Systemだけ対象URLのWindows/.NET選択を利用
- load_configとRequestsのmerge/selectを再利用するキー不要の内部helperで、認証前に実効選択を照合
- ProcessのHTTPS_PROXYだけを一時変更しtry/finallyで復元。競合・判定失敗・cleanup失敗は安全に停止
- 初回・日常・更新・再起動・VPN・ExecutionPolicyの手順と、Windows Desktop 5.1のmock/子プロセステスト

既存GET、schema、抽出条件、run公開を維持する。PAC取得等のOS通信はAPI処理と別。
複雑なPAC/failoverや資格情報自動送信は対象外。利用者の既存CLI実測と、新wrapperの自動検証、
未実施のQUICK2実機確認を区別する。PR-2以降の目的は変更しない。

## PR-2 第一段階: フォロー判定・ローカルレビュー出力（今回）

障害区分と発見日（検知・発見した日付）の設定ID2項目を一覧GETから限定選択します。
明示followup-configだけで、発見日から設定日数以上経過かつ現在未完了の行を「〇」とし、
全行へ対象/対象外/判定不能と理由を付けて同じCSV/JSONへ保存します。完了判定を優先します。
非影響・軽障害90日、中障害・重障害180日は匿名の初期例です。実ID/実区分値は利用者が設定します。
純粋な判定関数、厳格TOML、JST固定基準日、入力・ルールハッシュ、件数整合、既存run一括公開、
Windowsの固定引数伝搬を実装します。フォロー未指定時の既存schema・GET条件を維持します。

日数到達基準で、到達日を迎える月の月次判定、延長、期限後完了評価、承認確認は後続です。
〇は期限違反や状態変更の可否を意味しません。詳細schemaと未実施の実機受入は
[followup.md](followup.md)を参照します。HTTPモック試験とQUICK2実機合格を区別します。

当初PR-2の一般的な変更候補生成、dry-run変更案、二者レビュー、再取得時の差分検証は後続に残します。
今回の入力スナップショット識別は保存した許可入力のハッシュまでです。通知、別ファイル、GUI、
汎用ルールエンジン、オフライン再判定コマンドは追加せず、この段階でもRedmineを変更しません。

## PR-3 ウォッチャー追加（計画のみ）

QUICK2の対象プロジェクトで初めて検出したチケットについて、ローカルのユーザーIDリストを使って
ウォッチャー追加計画を作成し、承認済みの組だけを追加する。PR-3a（検出）、PR-3b（差分計画）、
PR-3c（承認後の実行）の順に進める。PR-2のフォロー判定は発見日からの経過日数と現在の完了状態を扱い、
PR-3aは一覧での初回検出を扱う。初期用途ではPR-2の出力を必須としない。将来はフォロー対象を別の
候補入力として利用できるようにし、PR-2の判定ロジックと既存CSV/JSON仕様を維持する。

現行の読み取り専用CLIが実装済みのAPIは `GET /users/current.json`、`GET /issues.json`、
`GET /projects/{id_or_identifier}.json` の3種類。PR-2のフォロー判定・ローカル出力も実装済み。
既存CLIの手動プロキシ指定によるextended出力とGUI照合、親のみと子を含む場合の件数差は確認報告がある。
新しい起動補助でのQUICK2確認とPR-2の実機受入は未実施。PR-3a〜PR-3cは未実装で、以下の実機確認も未実施。
既存の確認範囲は [Windows 11確認手順](windows-quick2-verification-runbook.md) と
[PR-2の手動受入](followup.md#手動受入未実施) を参照する。

### PR-3a 新規チケット検出・処理状態管理（GETのみ）

- **取得範囲**　既存の `GET /issues.json` と `fetch_issues` の固定ソート・ページング・上限を優先して再利用する。
  接続先と確認済みの数値プロジェクトIDを明示し、IDの照合には既存の `GET /projects/{id_or_identifier}.json` を使う。
  完了を含む全ステータス (`status_id=*`) を対象とし、初期範囲は指定プロジェクトのみ (`subproject_id=!*`) とする。
  応答の所属プロジェクトIDも照合し、不一致や欠損があれば停止する。子を含める運用は、対象IDの範囲と
  QUICK2でのフィルター挙動を確認してから、明示的に承認した別の取得範囲として扱う。
- **初回と差分**　明示的な初期化で、検証済み全ページのチケットID集合をベースラインとして保存する。
  初回に見えていたチケットは追加候補から除く。2回目以降は最後に正常保存した取得結果との差から
  増分を求め、過去に観測済みのIDの再出現を除いて初回検出候補とする。初回検出は、新規作成とは別の事実である。
  プロジェクト移動や閲覧権限の変更でも既存チケットが初めて現れ得るため、差分だけで新規作成と断定せず、
  範囲や可視性の変化に由来する可能性がある候補は保留して確認する。
- **保存と再開**　承認済みのリポジトリ外の保存先に、接続先・プロジェクト・子の扱い・閲覧主体に対応する
  取得範囲、前回成功時のID集合、過去の観測ID、検出時刻、処理状態を保存する。検出済み、承認待ち、
  追加完了、処理失敗、実行結果不明を区別し、未処理・保留は一覧の差分とは別に保持する。
  検出結果は対象範囲、候補IDと件数、引き継いだ未処理件数をローカルで確認できるようにする。
  SQLiteなどを比較し、保存方式・スキーマ、同じ状態への同時起動防止、スナップショットと候補の原子的な保存、
  バックアップ・復旧時の照合方法を実装前に決める。既存状態の消失・破損時は停止し、明示的に復旧する。
- **受入条件**　初回は候補0件。正常保存後から次の成功実行までに対象範囲に現れ、次回も取得できるIDは、
  PCシャットダウン・週末・休日を挟んでも検出できる。停止中に削除・移動・非表示となり取得できないIDは検出できない。
  API失敗、重複ID・件数・ページングの不整合、上限超過、状態保存失敗では停止し、前回の状態と未処理候補を保つ。
  取得中に件数が一致しても完全なスナップショットは保証されない。途中失敗からの再実行でも候補は消失・重複しない。
  POST/PUT/PATCH/DELETEは使用しない。
- **実機確認と拡張**　QUICK2のバージョン・独自改修、数値プロジェクトID、全ステータス・子の除外、
  件数と所属のGUI照合、ページ上限・取得負荷、権限変更・移動・削除時の可視性を確認する。既知の範囲・権限変更では
  既存状態での比較を中断し、未処理候補を保持したまま再ベースライン化の要否を確認する。一覧から消えたIDは
  観測履歴に残し、未処理分は保留する。再ベースライン化の手順と、移動・削除・一時的な非表示の切り分けは実装前に決める。
  `created_on` での絞り込みは日時境界や取りこぼしを検証したうえで、将来の取得負荷削減策として検討する。

### PR-3b ウォッチャー確認・差分追加計画（GETのみ）

- **入力**　PR-3aから引き継いだ未処理候補、確定した取得範囲、UTF-8のローカルテキストファイルを使う。
  移動や権限変更などで保留中の候補は、対象範囲と追加可否を確認するまで計画に含めない。
  1行にRedmineの正の10進数値ユーザーIDを1つ記載する。先頭のUTF-8 BOM、CRLF/LFを受け入れ、空行を読み飛ばし、
  重複IDを集約する。不正な整数、不正なUTF-8、読み込み失敗、サイズ・行長・件数の上限超過では計画作成を停止する。
  空の有効リストから追加操作は生成しない。上限値は実装前に決める。IDと利用可否は実環境で事前に確認し、
  氏名・メールアドレスからの自動推定は初期範囲外とする。
- **取得と差分**　固定の `GET /issues/{issue_id}.json?include=watchers` を候補とし、返却されたチケットID、
  所属プロジェクト、ウォッチャーID一覧を検証する。追加候補は希望ID集合から既存ウォッチャーID集合を引いた差分とする。
  権限不足、取得失敗、一覧の欠損・不正、可視性が確認できない応答では計画作成を停止する。
  空集合として扱えるのは、必要な閲覧権限の下で完全な空リストと確認できた場合に限る。
- **出力と承認**　dry-runを既定とし、対象チケットID、追加候補ID、既存登録済みID、追加操作件数
  （チケットIDとユーザーIDの組数）をローカルでレビューできるようにする。レビュー待ちは承認待ちとして保持する。
  入力、接続先・対象範囲、候補と計画内容を結び付けるハッシュ等の識別方法を検討する。承認はその識別子と
  対象の組にひも付け、承認者・承認時刻とともに記録する。入力・範囲・計画の変更時は再承認を求める。
- **受入条件と実機確認**　BOM・空行・重複・不正値・上限超過を検証し、既存登録済みのIDを候補から除外できること、
  ウォッチャーを確認できない場合に適用可能な計画を公開しないことをHTTPモックで確認する。
  QUICK2ではAPIの公開可否、閲覧権限、応答構造、独自改修、一覧の完全性、0件と非表示・欠損の違い、
  数値ユーザーIDの実在と対象チケットへの追加資格を確認する。PR-3bは承認後も変更系APIを実行しない。

### PR-3c 承認済みウォッチャーの限定追加

- **APIと実装前の条件**　標準Redmineの `POST /issues/{issue_id}/watchers.json` を候補とする。現行の
  [AGENTS.md](../AGENTS.md) は明示したGETのみを認める。PR-3c実装に先立ち、許可するPOSTを固定し、
  読み取り専用クライアントから独立した書き込み専用モジュールまたはCLI、許可範囲、必要なルール変更をレビュー・承認する。
  それまでは現行の読み取り専用制限を適用する。
- **実行前照合**　明示的な実行指示とPR-3bの承認済み計画の照合を必須とする。`GET /users/current.json` で
  実行主体を再認証・確認し、実行直前にチケットとウォッチャーを再取得して接続先、チケットID、所属、可視性、
  承認時からの重要な変更を確認する。プロジェクト違い、取得失敗、承認時に登録済みだった希望IDの消失などを
  検出したら停止し、再計画・再承認する。重要変更の判定基準は実装前に確定する。承認後に登録済みとなった
  IDはスキップし、承認済みの組のうち未登録のものだけを実行する。組数に明示上限を設け、初期は少数件に限定する。
- **結果と再開**　同じ状態・対象に対する同時実行を防ぎ、送信前に計画ID、実行主体、対象の組、時刻、試行を
  ローカルへ保存する。成功・失敗・スキップ・結果不明を組ごとに記録し、POST成功の応答後もGETで登録を照合して
  追加完了とする。タイムアウト、送信後の中断、照合・保存失敗などで結果が不明なら停止して記録を保持し、再取得する。
  登録を確認できれば再送しない。未登録を確認し、先の処理が後から反映されないと判断できる場合に限り、承認と範囲を
  再照合して再試行する。判断できない場合は保留する。一部失敗からの再開時は監査記録と取得結果を突き合わせ、
  完了・スキップ済みを除き、承認範囲内の未処理と再試行可能な組だけを続行する。
- **受入条件と実機確認**　未承認・改変・上限超過・範囲不一致ではPOSTを送らず、既存登録済み、部分失敗、中断、
  結果不明からの再実行でも二重追加を防げることをHTTPモックで検証する。事前GETとPOSTには時間差があるため、
  QUICK2の承認済みテスト環境で、API仕様・バージョン・独自改修、最小権限、応答と反映の確認方法、
  同時追加・重複時の挙動、通知の発生と通知対象への影響を少数件で確認してから本番利用を判断する。

### PR-3共通の運用とPR-4との境界

- 公開リポジトリやPRに実URL、実ID、社内情報、実レスポンスを残さない。入力・状態・計画・監査記録は
  リポジトリ外の承認済み保存先でアクセス制御と保管期限を適用する。APIキーは環境変数または非表示入力から
  取得し、コード・設定・監査ログへ保存しない。ログには認証情報、チケット本文、応答全文を含めない。
- HTTPS、CA証明書検証、リダイレクト拒否、既存プロキシ方針を維持し、HTTP操作を固定エンドポイントに限定する。
  Windows 11 / PowerShell 5.1のInherit/System、パス解決、プロキシの事前照合・復元、停止時の終了状態との
  整合を確認する。自動テストはHTTPモックを用い、QUICK2での実機受入と区別して記録する。
- PR-3の変更対象は承認済みウォッチャーの追加に限る。ウォッチャー削除は対象外とし、ステータス変更の
  ワークフロー・承認・競合処理はPR-4で扱う。PR-3での承認をPR-4の変更に流用しない。

## PR-4: ステータス変更（計画のみ）

ワークフロー、ロール、必須項目、ロック/同時更新、許可遷移、コメント要否を実機検証します。チケットIDと期待する更新時刻を含む承認済み候補だけを対象にし、実行直前再取得、競合停止、小バッチ、明示確認、監査記録、ロールバック不能時の手順を設計します。作成・削除や汎用API操作は対象外のままです。

## 各PRのゲート

1. テスト環境で最小権限の専用アカウントを使用する。
2. API/画面の件数・値、子プロジェクト、カスタム項目、権限を照合する。
3. セキュリティ、業務所有者、運用担当の承認を得る。
4. 本番は承認済み保存先・CA・proxyを使い、少数件から開始する。
5. 実測結果と未確認事項を記録し、架空の合格記録を作らない。
